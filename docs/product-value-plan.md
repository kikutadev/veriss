# veriss フォーク版 — 製品価値から逆算した開発計画

Status: **Phase 0/1リリース済み、Phase 2/3未完了** (2026-11-22)。現行のフォーク `main` (`ad2f316`) を起点にした製品化の計画。技術研究の進捗率とは分離する。

## 1. ユーザーが買う／採用する価値

対象者: Web フロントエンド開発者。とくにレスポンシブな CSS を書き、特定の画面幅・状態だけで起きる破綻を再現・修正したい人。

**約束すること**: 「一部の画面幅で起きるレイアウト破綻を、対応範囲全体の静的検査で反例付きで見つける」。ブラウザでの単一点テストや一般的な CSS 構文 lint を置き換えるとは言わない。現時点では CSS/DOM を明示的に与える閉じたモデルに対する主張で、任意のライブサイト／JS アプリ全体の検証ではない。

ユーザーが達成すべき行動:
1. **最初の1分**: 公開サイトを開き、狭い幅で3列がはみ出す NG と可変トラックの OK を選択。エラー・反例条件・原因が分かり、差分がなくなったことを確認できる。
2. **初回の自分の入力**: HTML と CSS をペーストし、検査する幅の範囲を指定して実行。エラー、警告、Unknown を別々に確認できる。根拠のない「検証済み」を返さない。
3. **自分の開発環境**: HTML/CSS ファイルを CLI で検査し、診断を JSON と可読形式で受け取る。正常／違反／未証明／入力エラーが判別可能で、CIで安全に判定できる。

## 2. 価値を測る指標（実測がないものは「達成」としない）

| 指標 | 合格条件 | 計測方法 |
| --- | --- | --- |
| 初見の成功 | 入口から NG→OK 切替を3操作以内に完了、反例または失敗条件を確認できる | 公開URLの実ブラウザ操作 |
| 診断の正確な表示 | エラー・警告・Unknown の件数が実際の診断と一致、エラーありで「警告0件」を成功と誤読させない | NG、OK、Unknown と入力編集の回帰 |
| CLI導入 | 既存パッケージから直接 `veriss check --html ... --css ...` 相当を実行可能。Git依存でも手順が完結 | クリーンな利用側で再現 |
| CLI終了コード | `verified=0`、`violated=1`、`unknown=2`、不正入力・内部障害=`3`。警告を含む verified は判定可能なまま区別 | 統合テスト |
| 一般化の実証 | 少なくとも3つの異なる実UI入力（自作だけでなく第三者例を含む）で発見・Unknown・対照を記録 | 原入力・判定・反例・修正後・ブラウザ観測を同じ記録に残す |
| 安全性 | 複雑なCSS、未対応JS、文字幅不明やOS差を verified に格上げしない | ネガティブケースと既存gate |

運用時の成功指標（まず計測する）: 初回導入の操作数、再現したエラー数、修正完了率、Unknown の主因、誤検出。ルール総数、型ファイル数、テスト件数を製品価値の代理指標にしない。

## 3. 実装の順序と詳細仕様

### Phase 0: 体験を成立させる（最優先）

- [x] デモの初期サンプルを **固定トラックでのはみ出し→可変トラックで修正** にする。既存サンプル・F116等は残す。第一画面に「何が・どの幅で・なぜ壊れるか」を表示する。ブラウザ上で実際のverissエンジンを呼び、硬い文字列で判定を演出しない。
- [x] UI結果は `エラーN / 警告N / UnknownN` を正しく表示。失敗状況と `verified / violated / unknown` を明瞭に分ける。無警告でも error がある場合は成功と表示しない。
- [x] ペーストしたHTML/CSSについては明示的な制約（フラグメント・外部スタイルシート・JS実行なし）を短く提示。例の内在的な box 契約は自由入力に使わない。
- [x] スマホ幅の UI と 3つの判定（NG／OK／Unknown）、critical CSS 抽出を公開 URL で操作確認してから Pages を更新。

### Phase 1: プロジェクトで試せる CLI（高）

- [x] コアの `analyzeHTML` と既存のZ3検算 API を再利用し、HTML/CSSをファイル指定で読み込む小さなCLIを用意する。新しい解析器は作らない。ファイルパスと `--min-width` / `--max-width`、`--json` のみで始める。将来の自動探索・設定ファイル・ライブURLクロールは作らない。
- [x] レポートは `status`、`counts`（error/warning/unknown）、診断 code/message/box、可能なら幾何の反例・条件を保持。内部ツリーの任意深度全探索は重複・ノイズの原因になるため意味上の診断位置を特定し、未確定の証明を断言しない。
- [x] プロジェクト外からの実行、Unknown、構文不正、ファイル欠落、正常系のテストを追加。配布方法は、現行のGit-pinned packageを前提にまず完成させ、npm公開は別の配布判断とする。
- [x] README 冒頭に最小のCLI体験と入力制限を追加し、最初のコマンドと期待する出力を実例で示す。

### Phase 2: 実UIに対する価値の証拠（高）

- [ ] ポートフォリオ、ブラウザゲームのUI、公開されている第三者UIサンプルの少なくとも3種類から**再現可能なHTML/CSS入力**を作る（実サイトの一部を抽出した場合はその限界を明記）。
- [ ] NG/OKでエラーが変わること、3ブラウザーの実測、Unknown率・入力準備の手間を記録。発見できなかった例も記録し、良い結果だけ選ばない。
- [ ] Webへ最大3つの検証ストーリーを掲載。詳細な420ルールの索引は下部の資料とし、製品価値のトップ体験を遮らない。

### Phase 3: 自動導入と形式証明の統合（P0–P2の受入後）

- [ ] React/Vue/Svelte の既存 adapter へ CLI 入口を接続し、有限状態やユーザー定義の契約を無理なく選択できるようにする。
- [ ] Lean 独立チェッカーとの型付き証明書の受け渡しを設計・検証。抽出した意味論と原コードの対応が成立する範囲にだけ保証表示を広げる。
- [ ] CSS被覆・フォント実測を実例の `Unknown` 上位原因から改善。Unknownを隠すために判定条件を緩めない。

## 4. 判断・範囲・受入ゲート

- Webのサンプルは実行可能な実コードの出力を表示し、静的画像や作り物の「成功」を使わない。
- レイアウトの反例幅は、実際の報告から得られた値だけを表示。得られない場合は「反例幅未確定」と明記。
- ファイルだけから任意の実サイト全体、React の実行時 DOM、JS到達状態、全CSSの正しさを推論しない。
- ブラウザ検証でOS依存のものは条件を示し、Unknownは失敗でも成功でもない。
- リリース条件: 型チェック・単体テスト・既存 `tools/gate.sh` と3ブラウザーE2Eの成功／残差の明示、配布対象でのCLIのエンドツーエンド、公開した Pages で NG→OK→Unknown の実操作。作業中ブランチの変更は触らない。
- 未達の Phase を「完了」と表示しない。変更内容を `docs/handoff.md` に記録する。

## 6. 追加優先機能: URLを貼って検証 (2026-11-22)

ユーザーからの要望により、P2の評価対象に入る前に **URL入力を最短の導入経路** として追加する。既存のHTML/CSS貼り付け・CLI・初期NG→OKデモは残す。

### 今回の到達条件

- [ ] 公開サイトの初画面でURL入力→検査ボタン→実際の結果を表示。入力したURLのHTML・外部CSS・styleタグを実際に取得する (架空の診断は使わない)
- [x] GitHub PagesはブラウザCORSを越えられないので、小さな公開HTTP取得Workerを用意。Workerは「公開ページの静的ソース収集」だけを担当し、verissの解析は既存ブラウザエンジンを再利用
- [x] URL入力→レスポンス→HTML/CSS解析で、完全にモデル化できていないケースは `UNKNOWN` と説明する。script、CSS未取得、@import、容量上限は被覆不足と表示。検出された具体的エラーはUnknownと併記し、成功とはみなさない
- [x] URLのpublic HTTP(S)・標準ポートを対象。内部アドレス、明示的認証情報、非標準ポート、巨大レスポンスを拒否。リダイレクト先・CSSの個別URLも同じ検査を通す。短時間で打ち切る
- [x] 実Webサイト複数種とNG/OKの固定フィクスチャで検証し、スマホでの操作・ブラウザでの入力状態・公開エンドポイントのHTTPレスポンスを確認してから公開
- [ ] 既存のゲートに加えて新しい収集層・UIの回帰テストを通す。公開先、対応範囲、利用制限をREADMEとサイトに記載する

### v1の線引き

**ページをレンダリングして実行時DOMを証明する機能ではない**。まず静的HTTPレスポンスのHTML/CSS取得を提供する。JSによるDOM生成、ページ遷移、CSS-in-JS、外部フォント・画像の実測、認証サイト等は検査範囲外。ブラウザ再現モードは独立した拡張として、ユーザーに価値のある報告ができた後に判断する。Web用に別のレイアウト検証器を作らない。

この追加は以前の「URLクロールは将来」の段階的優先順位を、ユーザーの最短導入ニーズに合わせて修正したもの。
