# veriss フォーク版 — 製品価値から逆算した開発計画

Status: **Phase 0/1リリース済み、Phase 2/3未完了** (2026-11-22)。現行のフォーク `main` (`ad2f316`) を起点にした製品化の計画。技術研究の進捗率とは分離する。

## 1. ユーザーが買う／採用する価値

対象者: Web フロントエンド開発者。とくにレスポンシブな CSS を書き、特定の画面幅・状態だけで起きる破綻を再現・修正したい人。

**約束すること**: 「一部の画面幅で起きるレイアウト破綻を、対応範囲全体の静的検査で反例付きで見つける」。ブラウザでの単一点テストや一般的な CSS 構文 lint を置き換えるとは言わない。現時点では CSS/DOM を明示的に与える閉じたモデルに対する主張で、任意のライブサイト／JS アプリ全体の検証ではない。

ユーザーが達成すべき行動:
1. **最初の1分**: 公開サイトを開き、狭い幅で3列がはみ出す NG と可変トラックの OK を選択。エラー・反例条件・原因が分かり、差分がなくなったことを確認できる。
2. **初回の自分の入力**: HTML と CSS をペーストし、検査する幅の範囲を指定して実行。エラー、警告、Unknown を別々に確認できる。根拠のない「検証済み」を返さない。
3. **自分の開発環境**: HTML/CSS ファイルを CLI で検査し、診断を JSON と可読形式で受け取る。正常／違反／未証明／入力エラーが判別可能で、CIで安全に判定できる。

## 2. 価値を測る指標（実測がないものは「達成」としない）

| 指標 | 合格条件 | 計測方法 |
| --- | --- | --- |
| 初見の成功 | 入口から NG→OK 切替を3操作以内に完了、反例または失敗条件を確認できる | 公開URLの実ブラウザ操作 |
| 診断の正確な表示 | エラー・警告・Unknown の件数が実際の診断と一致、エラーありで「警告0件」を成功と誤読させない | NG、OK、Unknown と入力編集の回帰 |
| CLI導入 | 既存パッケージから直接 `veriss check --html ... --css ...` 相当を実行可能。Git依存でも手順が完結 | クリーンな利用側で再現 |
| CLI終了コード | `verified=0`、`violated=1`、`unknown=2`、不正入力・内部障害=`3`。警告を含む verified は判定可能なまま区別 | 統合テスト |
| 一般化の実証 | 少なくとも3つの異なる実UI入力（自作だけでなく第三者例を含む）で発見・Unknown・対照を記録 | 原入力・判定・反例・修正後・ブラウザ観測を同じ記録に残す |
| 安全性 | 複雑なCSS、未対応JS、文字幅不明やOS差を verified に格上げしない | ネガティブケースと既存gate |

運用時の成功指標（まず計測する）: 初回導入の操作数、再現したエラー数、修正完了率、Unknown の主因、誤検出。ルール総数、型ファイル数、テスト件数を製品価値の代理指標にしない。

## 3. 実装の順序と詳細仕様

- [x] ペーストしたHTML/CSSについては明示的な制約（フラグメント・外部スタイルシート・JS実行なし）を短く提示。例の内在的な box 契約は自由入力に使わない。
- [x] スマホ幅の UI と 3つの判定（NG／OK／Unknown）、critical CSS 抽出を公開 URL で操作確認してから Pages を更新。

- [x] README 冒頭に最小のCLI体験と入力制限を追加し、最初のコマンドと期待する出力を実例で示す。

### Phase 2: 実UIに対する価値の証拠（高）

- [x] 公開Webには実UI3件の結果と範囲を短く掲載し、再現方法をリンク。既存デモの主役は維持。

### Phase 3: 自動導入と形式証明の統合（P0–P2の受入後）

- [ ] React/Vue/Svelte の既存 adapter へ CLI 入口を接続し、有限状態やユーザー定義の契約を無理なく選択できるようにする。

## 4. 判断・範囲・受入ゲート

- Webのサンプルは実行可能な実コードの出力を表示し、静的画像や作り物の「成功」を使わない。
- レイアウトの反例幅は、実際の報告から得られた値だけを表示。得られない場合は「反例幅未確定」と明記。
- ファイルだけから任意の実サイト全体、React の実行時 DOM、JS到達状態、全CSSの正しさを推論しない。
- ブラウザ検証でOS依存のものは条件を示し、Unknownは失敗でも成功でもない。
- リリース条件: 型チェック・単体テスト・既存 `tools/gate.sh` と3ブラウザーE2Eの成功／残差の明示、配布対象でのCLIのエンドツーエンド、公開した Pages で NG→OK→Unknown の実操作。作業中ブランチの変更は触らない。
- 未達の Phase を「完了」と表示しない。変更内容を `docs/handoff.md` に記録する。

### URL検証の非採用（2026-11-22）

任意の公開URLをブラウザ上の静的GitHub Pagesだけで取得することはCORSにより一般には不可能。Cloudflare Workerはリクエスト枠を消費するため、ユーザーの判断でURL入力と取得Workerを公開・コードともに撤回した。Workerは削除し、URL機能導入前のデモ（HTML/CSS直接入力、NG→OK、CLI）へ戻した。実装記録はGit履歴と `url-first-site-check` ブランチに残るが現行の製品機能には含めない。

### Phase 2e: ログイン後の権限別UI契約（2026-11-23）

- **目的:** 実アプリのAdmin/Manager/ViewerでUsers画面を見比べ、編集/停止という**操作を許す・禁止するUI状態**を検査できるようにする。認証済みページを渡す既存Playwright方式を維持。
- **完了条件:** 公開RBACデモで権限別に同一セレクタを検査し、Adminは操作可能、権限のない役割はネイティブdisabled・inert・非表示など実際のUI阻止を示す。誤設定した対照で観測違反を検出する。Chrome/Firefox/WebKitで比較し、`verifyUI`は実測の成功/失敗と静的Unknownを分離する。
- **設計境界:** これは**フロントエンドのUI操作可能性**であって、サーバAPIの認可強度の証明ではない。`aria-disabled`のみ・CSS `pointer-events:none` の見た目だけを確実なアクセス禁止と認めない。第三者のデータ操作・変更・Worker・新しいファイル/URL入力UIを増やさない。検証対象のセレクタ/状態名以外のDOM本文、ユーザー情報、認証情報は観測結果に残さない。
- **作業順:** 実デモの実測 → TDDで小さい共通観測API → 負例/対照を3ブラウザで検査 → 実デモを同じAPIで横断 → 正式ゲート→フォークmain/公開ページへ反映。

### Phase 2e 実装結果（2026-11-23）

- [x] RBAC公開デモのAdmin・Manager・Viewer 3権限を390/1280px×3ブラウザで実測。Adminの編集8/8有効と停止7/8有効という例外を識別し、Manager/Viewerは両操作群がすべてdisabled。外部E2E 9件で状態別の操作可能性を照合。
- [x] `captureControlAvailability` の共通observerで `all-enabled` / `some-enabled` / `all-blocked` を既存のveriss `Observation` 契約へ渡す。disabled/inert以外の見た目だけによる禁止は不確定、閲覧専用で有効化された対照は失敗。3ブラウザのオフライン負例で検算。静的全状態証明・サーバ認可は対象外。
- [ ] 次の候補: 権限別UIの**操作後に見せる画面**や、フォーム入力エラー状態の検証。現在の導入はE2E手動状態定義に依存しており、JS実装から全遷移の自動列挙は未対応。

### Phase 2f: ブラウザE2Eと静的証明の責務整理（設計検討・2026-11-23）

- **ゴール:** ログイン後UIで見つかった問題を検査し続けながら、Playwrightの通常のassertionを `Observation.passed` に包むだけの重複を減らす。veriss固有の価値は閉じたHTML/CSS・状態・環境を入力にした全域証明と反例に集中する。
- **今回の完了条件:** 現行APIとテストの重複/欠落を実コードで特定し、維持・移行・削除対象をファイル単位で決める。`ブラウザで実測した失敗 -> 同じ状態のソースを閉じる -> 既存domGeometry / verifyUIで静的契約` の実現条件・Unknownの境界・段階的移行テストを設計する。**現行実装や公開UIは今回変更しない。**
- **順序:** 現行コード・既存の部分幾何/状態証明例・Playwright既存機能の照合 -> 新しいアーキテクチャ判断をADRに記録 -> 次の小さい実装計画へ落とす。静的証明器、JS一般抽象解釈器、ログイン自動取得サービスを作り直さない。
- **詳細設計:** [ADR-0021: ブラウザ観測と静的証明の責務分離](adr/0021-browser-observation-proof-boundary.md)（Proposed）。変更候補はP0「E2Eの不要な真偽値ラッパーを減らす」→P1「矩形観測の重複整理」→P2「実装ソースから閉じた1状態/1対象の静的証明」。今回は設計のみ。
